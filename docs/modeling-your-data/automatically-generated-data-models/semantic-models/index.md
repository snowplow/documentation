A semantic model describes what the table of an [autogenerated data model](/docs/modeling-your-data/automatically-generated-data-models/index.md) means: what each row represents, which [event specification](/docs/event-studio/tracking-plans/event-specifications/index.md) it belongs to, and what each column holds. It also defines an `event_count` metric for the table. AI agents and BI tools read it to write correct SQL against your data.

Snowplow generates the semantic model as an [Apache Ossie](https://github.com/apache/ossie) YAML document. Apache Ossie was formerly called Open Semantic Interchange (OSI), and is a vendor-neutral format of datasets, fields, and metrics. You can load it into Snowflake as a semantic view, or convert it for other tools.

:::note[Available through AI tools only]
You can generate semantic models from [Snowplow Assistant](/docs/ai/console-agent/index.md), or from any AI assistant connected to the [Snowplow MCP server](/docs/ai/snowplow-mcp/index.md). Console doesn't have a semantic model option yet.
:::

## Why use a semantic model

The warehouse stores your event data, but not its meaning. An agent querying the table sees column names such as `checkout_step_step_name`, with no way to know which rows are which business event or what the values stand for.

Your [tracking plan](/docs/event-studio/tracking-plans/index.md) already holds that information, in the event specification names, descriptions, and triggers, and in the property descriptions and allowed values of your [schemas](/docs/fundamentals/schemas/index.md). The semantic model takes that information and attaches it to the data model's table, where agents can read it.

Snowplow composes the semantic model from the tracking plan and the stored data model configuration. Nothing in it is inferred or generated by AI. If a property has no description in its schema, its field has no description in the semantic model.

### What the semantic model contains

Each part of the semantic model comes from the tracking plan or the data model configuration:

| Semantic model part | Source                                                                                                                                                  |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Document name       | The tracking plan name. In Snowflake, this becomes the semantic view name.                                                                             |
| Dataset             | The data model's table, named after the data model.                                                                                                    |
| Dataset description | The data model description, followed by what a row is, how to read the event specification columns, and each event specification with its ID, description, and triggers. |
| Fields              | One field per column of the data model, in the same order. Property fields use the schema property description and list allowed values from `enum`. Atomic fields use the [canonical event](/docs/fundamentals/canonical-event/index.md) descriptions. |
| Time dimensions     | `date`, `time`, and `date-time` properties, plus atomic timestamps such as `derived_tstamp`.                                                           |
| Metrics             | `event_count`, the number of distinct `event_id` values. This is the only metric.                                                                      |

The semantic model doesn't include relationships between tables, per-event-specification metrics, or `ai_context`.

## Generate a semantic model

Before you start, you'll need:

* A tracking plan whose event specifications have event data structures
* A Snowflake, BigQuery, Databricks, or lake destination for the pipeline that collects the tracking plan's events. Redshift isn't supported.
* Events that carry the `event_specification` entity, either from [Snowtype](/docs/event-studio/implement-tracking/index.md) or from [event specification inference](/docs/event-studio/tracking-plans/event-specification-inference/index.md)
* Snowplow Assistant, or an AI assistant connected to the [Snowplow MCP server](/docs/ai/snowplow-mcp/index.md)

Ask your assistant to create a data model and its semantic model for a tracking plan. For example:

```txt
Create a data model and semantic model for my "Checkout flow" tracking plan,
as a view on my Snowflake production destination.
```

The assistant uses the `autogenerated-data-models` skill to:

1. Read the tracking plan and list your destinations, to pick the warehouse the pipeline loads into
2. Ask whether your tracking code attaches the `event_specification` entity to every event, for example because you use Snowtype. This decides how the data model filters events. See [event specification inference](/docs/modeling-your-data/automatically-generated-data-models/index.md#event-specification-inference).
3. Create the data model and show you its SQL
4. Generate the semantic model for the table, and give you the steps to load it into your warehouse

The assistant can't run SQL in your warehouse. You'll run the data model SQL yourself, or add the dbt model to your project, before you load the semantic model.

You can also generate a semantic model for a data model you created earlier, in Console or through the API:

```txt
List the data models for my "Checkout flow" tracking plan, then give me
the semantic model for checkout_events.
```

For a dbt model, or a view over a custom atomic events table, the assistant needs to know where the table lives. This includes every lake and Databricks volume destination. Tell it the fully qualified table name:

```txt
Give me the semantic model for checkout_events. I materialized it with dbt
as analytics.snowplow_derived.checkout_events.
```

:::note[Semantic models follow the stored data model]
The data model SQL is a snapshot of the tracking plan when you created it. The semantic model describes that snapshot. When the tracking plan changes, create a new data model, rebuild its table, and generate a new semantic model.
:::

### Example semantic model

This example is part of a semantic model for a `Web Analytics` tracking plan, on Snowflake:

```yaml
version: 0.2.0.dev0
name: web_analytics
datasets:
- name: web_events
  source: analytics.atomic.web_events
  description: |-
    One row per event tracked for the 'Web Analytics' tracking plan.

    The event_specs column lists the event specifications recorded against a row by the event specification enrichment, and is empty when the enrichment is not enabled.

    Event specifications:

    - User workflow events (d00312cb-d1bd-42e4-9429-e7fefca14476)
  fields:
  - name: event_id
    expression:
      dialects:
      - dialect: SNOWFLAKE
        expression: event_id
    dimension:
      is_time: false
    description: A UUID for each event
    datatype: String
  - name: derived_tstamp
    expression:
      dialects:
      - dialect: SNOWFLAKE
        expression: derived_tstamp
    dimension:
      is_time: true
    description: Timestamp making allowance for inaccurate device clock
    datatype: DateTimeTz
  - name: user_workflow_step
    expression:
      dialects:
      - dialect: SNOWFLAKE
        expression: user_workflow_step
    dimension:
      is_time: false
    description: 'Allowed values: "new_poll", "option_added", "vote_added".'
    datatype: String
metrics:
- name: event_count
  expression:
    dialects:
    - dialect: SNOWFLAKE
      expression: count(distinct web_events.event_id)
  description: Number of events tracked for the 'Web Analytics' tracking plan.
  datatype: Integer
```

## Load the semantic model into your warehouse

How you load the semantic model depends on where your agent or BI tool reads it from.

### Snowflake

Snowflake creates a semantic view directly from Apache Ossie YAML. Snowflake supports Ossie version `0.1.1`, so change the first line of the YAML from `version: 0.2.0.dev0` to `version: 0.1.1`. Then run:

```sql
CALL SYSTEM$CREATE_SEMANTIC_VIEW_FROM_OSSIE_YAML(
  'analytics.atomic',
  $$
version: 0.1.1
name: web_analytics
datasets:
  ...
  $$
);
```

The first argument is the database and schema to create the semantic view in. Use the schema that holds the data model's table. The `$$` quoting keeps the quotes and line breaks in the YAML intact.

Snowflake names the semantic view after the document `name`, here `web_analytics`. If you run the statement again with the same name, Snowflake replaces the semantic view and keeps its grants.

### Other tools

For Databricks metric views, Cube, Omni, and other tools, convert the YAML with the converters in the [Apache Ossie repository](https://github.com/apache/ossie). Each converter's documentation explains how to load the output.

## Query your data through the semantic view

Once the semantic view exists, Snowflake Cortex Analyst and any agent connected to your Snowflake account can use it to answer questions in natural language. The descriptions in the semantic view tell the agent which rows match each event specification, and which values a column can contain.

Example questions for the `Web Analytics` tracking plan:

```txt
How many polls were created each day last week?
```

```txt
What share of users who created a poll went on to add a vote?
```

```txt
Which day of the week do users pick most often in the meeting scheduler?
```

If you use Snowplow Assistant or the Snowplow MCP server to query your warehouse, the assistant checks for an existing data model for the tracking plan, and suggests generating a data model and semantic model if none exists.
